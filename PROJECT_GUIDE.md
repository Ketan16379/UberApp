# UberApp project guide

This document explains how this Spring Boot Uber-like application is organized and
how a ride moves through the system. It describes the current implementation, not
a generic Uber production architecture.

## 1. Technology and architectural style

The application is a layered Spring Boot application:

```text
HTTP client
   |
Controllers       REST endpoints, authentication and role checks
   |
Services          Business rules and transaction boundaries
   |
Strategies        Replaceable fare, driver-matching and payment algorithms
   |
Repositories      Spring Data JPA database access
   |
PostgreSQL/PostGIS
```

Important dependencies are Spring Web, Spring Data JPA, Spring Security, JJWT,
PostgreSQL, Hibernate Spatial, ModelMapper, Lombok, Springdoc OpenAPI and Actuator.
The project targets Java 21 and Spring Boot 3.5.5.

`UberAppApplication` is the Spring Boot entry point. Component scanning discovers
classes annotated with `@Service`, `@Component`, `@Repository`, `@RestController`
and `@Configuration`, and Spring injects their dependencies through constructors
generated by Lombok's `@RequiredArgsConstructor`.

## 2. Package responsibilities

| Package | Responsibility | Examples |
|---|---|---|
| `controllers` | Maps HTTP requests to service calls; selects status codes and DTOs | `AuthController`, `RiderController`, `DriverController` |
| `services` | Interfaces defining business operations | `RideService`, `PaymentService` |
| `services.impl` | Business implementations and transaction boundaries | `RiderServiceImpl`, `DriverServiceImpl` |
| `strategies` | Strategy interfaces and managers that select an algorithm | `RideStrategyManager`, `PaymentStrategyManager` |
| `strategies.impl` | Concrete algorithms | surge fare, nearest driver, wallet payment |
| `entities` | JPA database/domain models | `User`, `Ride`, `Wallet` |
| `entities.enums` | Controlled state and option values | `RideStatus`, `Role`, `PaymentMethod` |
| `dto` | API input/output shapes; prevents controllers exposing entities directly | `RideRequestDto`, `LoginResponseDTO` |
| `repositories` | Spring Data JPA interfaces and custom queries | `DriverRepository`, `RideRepository` |
| `utils` | Small reusable conversion/helpers, especially spatial values | `GeometryUtil` |
| `Security` | JWT parsing and request authentication | `JWTService`, `JwtAuthFilter` |
| `configs` | Spring beans and security/filter-chain configuration | `WebSecurityConfig`, `MapperConfig` |
| `advices` | Cross-cutting response and exception handling | `GlobalResponseHandler`, `GlobalExceptionHandler` |
| `exceptions` | Application-specific exceptions | `ResourceNotFoundException`, `RuntimeConflictException` |

## 3. Authentication and authorization

### Signup

`POST /auth/signup` is public.

1. `AuthController` receives `SignupDto`.
2. `AuthServiceImpl` rejects an existing email.
3. ModelMapper converts the DTO to `User`.
4. The new user receives the `RIDER` role and a BCrypt-encoded password.
5. A `Rider` profile and a `Wallet` are created in the same transaction.
6. A `UserDto` is returned with HTTP 201.

### Login

`POST /auth/login` is public.

1. `AuthenticationManager` checks the email and BCrypt password.
2. `JWTService` creates a short-lived access token and a longer-lived refresh token.
3. The access token is returned in `LoginResponseDTO`.
4. The refresh token is placed in an HTTP-only `token` cookie.

### Authenticated requests

`WebSecurityConfig` makes the application stateless, disables CSRF, permits
`/auth/**`, and requires authentication for every other route. `JwtAuthFilter`
runs before Spring's username/password filter:

```text
Authorization: Bearer <access-token>
        |
JwtAuthFilter -> JWTService parses subject (user id)
        |
UserService loads User
        |
SecurityContext stores User and authorities
        |
Controller and service code can identify the current user
```

Roles are converted to authorities such as `ROLE_RIDER`, `ROLE_DRIVER` and
`ROLE_ADMIN`. Controller-level `@Secured` annotations enforce:

- `/riders/**`: `ROLE_RIDER`
- `/drivers/**`: `ROLE_DRIVER`
- `/auth/onBoardNewDriver/{userId}`: `ROLE_ADMIN`

Note: the filter currently reads the access token from the `Authorization` header.
The refresh-token cookie is created at login but is not itself consumed by a
refresh endpoint in the current code.

## 4. Main ride lifecycle

The application uses two related records:

- `RideRequest`: the rider's request before a driver accepts it.
- `Ride`: the confirmed trip after a driver accepts it.

The normal state progression is:

```text
RideRequest: PENDING -> CONFIRMED
Ride:        CONFIRMED -> ONGOING -> ENDED
                         \-> CANCELLED
```

### A. Requesting a ride

`POST /riders/requestRide` (`ROLE_RIDER`)

1. `RiderServiceImpl` obtains the rider from `SecurityContextHolder`.
2. The request DTO is mapped to `RideRequest`.
3. Status is set to `PENDING` and the rider is attached.
4. `RideStrategyManager` chooses a fare strategy:
   - between 18:00 and 21:00: surge strategy, `distance * multiplier * 2`
   - otherwise: default strategy, `distance * multiplier`
5. Both strategies call `DistanceServiceOSRMImpl`, which calls the public OSRM
   routing API and converts metres to kilometres.
6. The request, including its calculated fare, is saved.
7. The manager selects driver matching:
   - rider rating >= 4.8: nearby top-rated drivers
   - otherwise: ten nearest available drivers
8. The matching list is currently calculated but not notified or stored; the code
   contains a TODO for driver notifications.
9. The saved request is mapped to `RideRequestDto` and returned.

### B. Accepting a ride

`POST /drivers/acceptRide/{rideRequestId}` (`ROLE_DRIVER`)

1. The request is loaded and must still be `PENDING`.
2. The logged-in driver must be available.
3. Driver availability is saved as `false`.
4. `RideServiceImpl.createNewRide` changes the request to `CONFIRMED`.
5. A new `Ride` is copied from the request, assigned to the driver, set to
   `CONFIRMED`, and given a four-digit OTP.
6. The ride is saved and returned as `RideDto`.

The request path calls the variable `rideRequestId`; later driver operations use
the resulting ride id.

### C. Starting a ride

`POST /drivers/startRide/{rideRequestId}` with `RideStartDto.otp`

The service loads the ride, verifies that the logged-in driver owns it, checks
`CONFIRMED`, and compares the submitted OTP. It then:

1. records `startedAt`;
2. changes the ride to `ONGOING`;
3. creates a pending `Payment`;
4. creates an empty `Rating` record for the ride.

### D. Ending and paying

`POST /drivers/endRide/{rideId}`

The driver must own an `ONGOING` ride. The service records `endedAt`, changes the
ride to `ENDED`, marks the driver available again, and processes the payment:

```text
PaymentService
  -> PaymentStrategyManager(payment method)
  -> WalletPaymentStrategy or CashPaymentStrategy
```

- `WALLET`: deducts the fare from the rider and credits the driver with
  `fare * (1 - platform commission)`.
- `CASH`: does not deduct the rider wallet; it deducts the platform commission
  from the driver's wallet.

The payment is then marked `CONFIRMED`.

### E. Cancellation

Either participant can cancel a confirmed ride:

- `POST /riders/cancelRide/{rideId}`
- `POST /drivers/cancelRide/{rideId}`

The service verifies ownership, changes the status to `CANCELLED`, and makes the
driver available again. Cancellation is not allowed after the ride has started.

### F. Ratings

After a ride is `ENDED`:

- rider: `POST /riders/rateDriver`
- driver: `POST /drivers/rateRider`

`RatingServiceImpl` stores the corresponding rating, prevents duplicate ratings
for that side, calculates the average of historical ratings, and updates the
driver or rider profile rating.

## 5. Strategy pattern used by the project

The strategy interfaces keep business services independent of specific algorithms.
The managers select a Spring-managed implementation at runtime.

### Ride strategies

`RideStrategyManager` selects `RideFareCalculationStrategy` based on local time
and `DriverMatchingStrategy` based on the rider's rating. Adding another pricing
or matching rule normally means adding an implementation and updating the manager,
rather than rewriting `RiderServiceImpl`.

### Payment strategies

`PaymentStrategyManager` maps the `PaymentMethod` enum to:

```text
WALLET -> WalletPaymentStrategy
CASH   -> CashPaymentStrategy
```

This is useful because each payment method has different accounting effects while
`PaymentServiceImpl` only coordinates lookup and delegation.

## 6. Data model

The central relationships are:

```text
User 1--1 Rider
User 1--1 Driver
User 1--1 Wallet
Rider 1--* RideRequest
Rider 1--* Ride
Driver 1--* Ride
Ride 1--1 Payment
Ride 1--1 Rating
Wallet 1--* WalletTransaction
```

`User` implements Spring Security's `UserDetails`. Roles are stored as an eager
element collection in `user_roles`. `Ride` and `RideRequest` store pickup and
drop-off as PostGIS `Point` values with SRID 4326. The driver repository uses
`ST_DWithin` and `ST_Distance` to find nearby available drivers.

`GeometryUtil` converts the DTO coordinate array into a JTS `Point` with SRID
4326; `MapperConfig` registers this conversion with ModelMapper. Coordinates are
passed to OSRM as `longitude,latitude`.

Repositories also provide paginated rider/driver ride history through Spring Data
derived queries. Controllers default to page 0, size 10, newest first.

## 7. API map

| Method | Endpoint | Role | Purpose |
|---|---|---|---|
| POST | `/auth/signup` | Public | Create rider user, profile and wallet |
| POST | `/auth/login` | Public | Authenticate and issue JWTs |
| POST | `/auth/onBoardNewDriver/{userId}` | Admin | Add driver profile to a user |
| POST | `/riders/requestRide` | Rider | Calculate fare and create request |
| POST | `/riders/cancelRide/{rideId}` | Rider | Cancel confirmed ride |
| POST | `/riders/rateDriver` | Rider | Rate driver after ride |
| GET | `/riders/getMyProfile` | Rider | Read rider profile |
| GET | `/riders/getMyRides` | Rider | Paginated rider history |
| POST | `/drivers/acceptRide/{rideRequestId}` | Driver | Accept pending request |
| POST | `/drivers/startRide/{rideRequestId}` | Driver | Validate OTP and start ride |
| POST | `/drivers/endRide/{rideId}` | Driver | End ride and process payment |
| POST | `/drivers/cancelRide/{rideId}` | Driver | Cancel confirmed ride |
| POST | `/drivers/rateRider` | Driver | Rate rider after ride |
| GET | `/drivers/getMyProfile` | Driver | Read driver profile |
| GET | `/drivers/getMyRides` | Driver | Paginated driver history |

Successful responses are generally wrapped by `GlobalResponseHandler` in
`ApiResponse`. API documentation and Actuator responses are excluded from that
wrapper. `GlobalExceptionHandler` converts not-found, conflict, validation and
other exceptions into a consistent error response.

## 8. Configuration and running locally

1. Start PostgreSQL with the PostGIS extension available.
2. Create/use the database configured by `spring.datasource.url`.
3. Set the database password and JWT secret through environment-specific
   configuration; do not commit real credentials.
4. Run `mvnw.cmd spring-boot:run` on Windows, or build with `mvnw.cmd test`.
5. Open the generated Springdoc UI at `/swagger-ui/index.html` when the server is
   running.

The current properties use `spring.jpa.hibernate.ddl-auto=create`, so the schema
is recreated on startup. `data.sql` is then loaded. This is suitable for a
learning/demo environment, not for preserving production data.

## 9. How to read the code efficiently

For a new feature, follow this path:

1. Find its endpoint in a controller.
2. Open the service interface, then its `services.impl` implementation.
3. Follow injected strategy managers and service collaborators.
4. Inspect repository methods for database behavior.
5. Check the relevant entity and enum for persisted state.
6. Check the matching Mermaid diagram in `docs/diagrams`.
7. Check `GlobalExceptionHandler` and `GlobalResponseHandler` to understand the
   final HTTP response shape.

The existing Mermaid diagrams provide focused views of authentication, signup,
login, ride request, acceptance, start/end, cancellation, payment, ratings and
the entity relationship model.

## 10. Current implementation limitations to keep in mind

These are useful when debugging behavior:

- Driver matching returns candidates but does not send notifications.
- There is no visible endpoint for driver location updates.
- Refresh-token rotation/validation is not implemented; only access-token
  authentication is wired into the filter.
- `ddl-auto=create` resets the database each startup.
- Wallet deduction and transaction recording should be reviewed before treating
  the wallet as production accounting; the deduction path currently constructs a
  transaction with `CREDIT` and does not call the transaction service.
- Several domain validation failures currently use generic `RuntimeException`,
  which the global handler reports as HTTP 500 rather than a more specific 4xx.
- The driver start endpoint parameter is named `rideRequestId`, although the
  service method operates on the accepted ride id.
